# AGENTS.md

## Project

Firework is a lightweight pull-based orchestrator for Firecracker microVMs written in Go. 

## Layout

- `cmd/agent`: `firework-agent` entry point.
- `cmd/controlplane`: control-plane entry point.
- `cmd/fireworkctl`: operator CLI; depends on API contracts, not control-plane runtime code.
- `cmd/fc-init`: guest init process used inside microVM rootfs images.
- `internal/agentconfig`: agent operational config types, defaults, loading, and validation.
- `internal/config`: provider-neutral resolved workload config used by direct Git mode and the control plane.
- `internal/registryapi`: agent-to-control-plane registry wire types.
- `internal/operatorapi`: control-plane-to-operator response types.
- `internal/statusmodel`: bounded agent telemetry shared by the registry contract.
- `internal/enricher`: GitOps input expansion and defaults.
- `internal/scheduler`: placement and bin-packing logic.
- `internal/reconciler`: desired-vs-running VM plan/apply logic.
- `internal/agent`: node runtime.
- `internal/vm`: VM lifecycle.
- `internal/network`: host networking.
- `internal/controlplane`: registry/events/controller runtime.
- `internal/store`: Git and object-storage config backends.
- `internal/objectstorage`: provider-neutral S3/GCS operations.
- `docs/configs/`: source of truth for config formats.
- `docs/architecture/`: contains the main design/architecture details on the project.
- `examples/`: sample agent, control-plane, and node configs.

## Conventions

- Format Go with `gofmt -s` (run `make fmt`).
- Prefer table-driven tests for multi-case tests.
- The scheduler and enricher are pure functions — keep them that way.
- Keep integrations/dependencies (cloud object storage, Git, Firecracker,
  filesystem, etc.) behind interfaces.
- Keep `internal/operatorapi` standard-library-only. Keep `internal/registryapi`
  free of runtime dependencies. It may depend on `internal/statusmodel`.
- Do not import `internal/controlplane` from agent commands or clients, or
  agent runtime packages from the control-plane command.
- Version/commit/build time are injected via ldflags at build time; never hardcode them.
- When changing config schemas, CLI behavior, APIs, or user-visible runtime behavior, update `docs/`, `examples/`, and relevant tests.

## Shared contracts and regression checks

- When changing configuration, identity, ports, or image contracts, trace affected
  producers and consumers across `firework-deployment-example` and
  `firework-gitops-example`. Report required companion changes and rollout
  ordering; unrelated changes do not require a cross-repository audit.
- Runtime schema changes may require updating the GitOps workflow's pinned
  `configcheck` revision. Guest-init changes may require corresponding changes
  to GitOps's bundled `scripts/fc-init/main.go`.
- When changing desired-state handling, preserve the distinction between missing
  or unreadable configuration and an explicit `services: []`. Missing information
  must not become an instruction to stop workloads.
- For reconciliation or cache changes, cover success, transient failure, and
  recovery in sequence, including a previously populated cache. Deferred or
  partially published work must remain eligible for retry.
- When changing persisted configuration fields or JSON tags, inspect serialization
  and VM ownership hashes. If recovery compatibility is required, test with a
  pinned pre-change manifest/JSON and hash, not a fixture regenerated by the new
  serializer.

## Building

```bash
make build-agent        # bin/firework-agent
make build-controlplane # bin/firework-controlplane
make build-fc-init      # bin/fc-init (linux/arm64, static)
make build-all          # builds all the binaries
```

## Validation

Use the narrowest check that matches the change:

- Docs-only changes: inspect formatting/readability and links; verify changed
  commands, paths, defaults, and behavioral claims against implementation. No Go
  tests are required unless needed to resolve a specific behavioral uncertainty.
- Go code changes: run `make fmt`, `make test`, and `make lint`.
- Runtime, scheduler, reconciler, store, or control-plane changes: also run `make test-race`.
- Dependency or module changes: run `make tidy` and verify go.mod/go.sum diffs are intentional.
- Reconcile flow changes: run `make smoke-local`. It uses fake Firecracker and
  disables host network setup; it does not verify real guest boot or networking.

For CI-equivalent local validation run the logic/steps from `.github/workflows/ci.yaml`. 

Report which checks ran and any remaining runtime verification. Cloud deployment
is a separate, explicitly authorized validation step and can be batched across
changes; a green local or CI result does not establish deployed behavior.
